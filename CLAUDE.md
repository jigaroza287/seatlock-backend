# Seatlock backend

Ticket booking backend: catalog, seat booking, mock payments. Core problem: **no double booking under heavy demand**.

## Scope guard

- Don't add frameworks, libraries or infrastructure that aren't already in `package.json` or `docker-compose.yml`. Ask first.
- Build what the task needs, nothing for later stages.

## Stack (versions pinned on purpose)

| Tool | Version | Note |
| --- | --- | --- |
| Node | 24 (`.nvmrc`) | ESM only (`"type": "module"`) |
| pnpm | 12 | Never use npm or yarn |
| TypeScript | `~6.0` | typescript-eslint supports below 6.1; don't upgrade |
| Express | 5 | Forwards async errors; no `asyncHandler` wrapper |
| Zod | 4 | Validation and inferred types |
| Prisma | 7, with `@prisma/adapter-pg` | Stay on 7; the npm `latest` tag is the v8 RC with a different API |

| Vitest | 5 | Test runner |
| ESLint 10 (type-aware), Prettier 3 (+ `prettier-plugin-sql`) | | Lint and format |

## Commands

```bash
docker compose up -d   # Postgres on 127.0.0.1:5433, Adminer on 127.0.0.1:8080
pnpm dev               # watch mode, loads .env
pnpm typecheck         # tsc --noEmit
pnpm lint              # ESLint
pnpm format:check      # Prettier
pnpm test              # Vitest
pnpm build && pnpm start
pnpm db:generate       # regenerate the Prisma client after schema changes
```

Prisma config lives in `prisma7.config.ts` (non-default name).

## Layout

```
src/
  server.ts            entry: checks the DB, listens, graceful shutdown
  app.ts               Express app: middleware, routes, 404, error handler
  db/prisma.ts         Prisma client (pg adapter, pool settings)
  middleware/          request id, global error handler
  modules/<name>/      one folder per feature:
    <name>.routes.ts       paths to controller functions
    <name>.controller.ts   Zod parse, call service, HTTP response
    <name>.service.ts      business rules
    <name>.repository.ts   Prisma access
    <name>.schema.ts       Zod schemas
    <name>.type.ts         types and interfaces
  shared/              AppError, Prisma error mapping, shared schemas and types
  generated/prisma/    generated client: gitignored, never edit
prisma/                schema.prisma, migrations/
sql/                   schema.sql (original DDL), seed.sql, queries.sql (practice)
docs/                  api-contract.md, pg-errors.md
requests.http          manual API checks
```

## Layer rules

- **Routes:** map paths to controller functions. Nothing else.
- **Controller:** parse input with Zod `schema.parse`, call the service, shape the response. No database access.
- **Service:** business rules; throws `AppError`. No Express or Prisma types.
- **Repository:** the only layer that talks to Prisma. Maps rows to domain types and database errors to `AppError`.
- Errors go to `middleware/error.middleware.ts`. Controllers never send error responses themselves.

## Conventions

- Files: kebab-case, named `<module>.<layer>.ts`.
- Interfaces take an `I` prefix (`IEventRepository`); the implementing class gets the plain name (`EventRepository`). No implementation prefixes like `Prisma` in class names.
- Relative imports end in `.js` (NodeNext). Use `import type` for type-only imports.
- Env vars are read as `process.env['NAME']`. Document every new one in `.env.example`.
- Responses: `{ data }`; lists `{ data, pagination }`.
- Errors: `{ error: { code, message, details? } }`, built with `AppError` factories (`AppError.notFound`, `AppError.conflict`).
- Status codes: 201 with `Location` on create, 204 on delete, 400 for validation, 404 before 409 on update.
- Duplicates: rely on database unique constraints (Prisma `P2002` to 409). Never check-then-insert.
- Postgres error mapping follows `docs/pg-errors.md`.
- Money: integer minor units (paise), named `priceMinor` / `price_minor`. Never floats.
- Ids: UUID v7, generated by the database (`uuidv7()`).
- Time: `timestamptz` in UTC. Date filters use half-open ranges in the user's time zone, never `::date`.
- `docs/api-contract.md` is the source of truth for the API. If code and contract disagree, stop and ask which one changes.

## Database and migrations

- `prisma/migrations/` is the schema source of truth. `0_init` is a baseline of `sql/schema.sql`, marked as applied.
- Never edit a migration that has been applied. A schema change means a new migration.
- Prisma can't model CHECK constraints, constraint names or lookup rows. Add those to the migration SQL by hand.
- Run `pnpm db:generate` after changing `schema.prisma`.

## Testing (being set up)

- Vitest. Route tests use Supertest against `app` with the in-memory repository, no database.
- Integration tests run against a separate test database. Never point tests at the dev database.
- Keep `requests.http` in sync when routes or status codes change.

## Project rules

- Generic domain only: no real company names, customer data or payment gateways. Payments are mock only.
- No secrets in code or commits.
